# 一步一步做游戏

## 核心目标

带着用户完成一个真实可玩的游戏，而不止输出策划文档或代码片段。始终形成下面的闭环：

```text
需求 → 设计 → 实施计划 → 最小可玩闭环 → 测试 → 试玩反馈 → 迭代 → 交付
```

先确定当前所处阶段，然后只推进到下一个可验证成果。用户明确要求“继续”“开始实施”或“修复”时，直接行动；只有缺少会显著改变产品方向的信息时才停下来提问。

## 开始前

1. 检查工作区、需求文档、设计稿、截图、现有代码、测试和 Git 状态。
2. 判断请求属于新建、重做、扩展、修复、验收还是发布。
3. 创建或更新短计划，始终只保留一个进行中的步骤。
4. 读取 [first-principles.md](references/first-principles.md)，用其中的不变量约束设计。
5. 需要选择具体实施阶段时，读取 [stage-playbook.md](references/stage-playbook.md)。
6. 准备验收和交付时，读取 [verification-checklists.md](references/verification-checklists.md)。

不要在没有检查现有文件和用户改动的情况下重建项目。不要覆盖与当前任务无关的工作区修改。

## 第一步：把想法变成可执行定义

从用户的语言、附件或需求文档中提取：

- 玩家是谁、为什么玩；
- 一分钟内重复的核心动作；
- 胜利、失败、重试和奖励；
- 游戏状态与必须守恒的不变量；
- 平台、屏幕方向、输入方式和离线要求；
- 首个可验证版本明确不做什么。

如果用户只有一句想法，生成最小假设并清楚标注。优先问一个最能改变结果的问题，不连续盘问。

需要保存设计时，创建游戏设计说明，至少包含：目标用户、核心循环、状态模型、交互流程、内容结构、音频反馈、技术边界、验收标准。

## 第二步：制定能并行但可合并的实施计划

把工作拆成独立交付面：

- 领域规则与随机内容；
- 游戏画面与交互；
- 音频、存储、服务与测试；
- 集成与浏览器验收。

每项必须写清输入、输出、共享接口和完成条件。只有用户明确要求多 Agent 或环境规则允许时才使用子 Agent；把子任务限制为互不覆盖的文件或模块，主 Agent 负责读取需求、定义接口、集成、测试和最终提交。

先建立 Git 仓库只在用户需要版本控制或远端协作时进行。已有仓库时先检查远端、分支和工作树，不重复初始化。

## 第三步：实现最小可玩闭环

先做一条从开始到完成的纵向切片：

```text
开始 → 理解目标 → 执行主要操作 → 状态真实变化
→ 正确/错误反馈 → 完成 → 可以重玩
```

在扩充美术和关卡前验证：

- 玩家无需读长说明也能开始；
- 屏幕、动画、语音和判定读取同一游戏状态；
- 错误输入不会破坏已完成进度；
- 音效和语音在真实点击后可播放；
- 页面刷新、模块缺失或音频不可用时能安全降级。

优先实现领域模型和最薄 UI，再逐步增加表现。不要用 DOM 文本、动画计数或音频文案各自维护一套数值。

## 第四步：扩展关卡与随机内容

最小闭环通过后再扩展内容：

1. 把固定文案、固定数值和固定场景提取为任务数据。
2. 用受约束的生成器产生题目或关卡，而不是直接调用无约束随机数。
3. 为同一轮维护近期指纹，避免连续重复。
4. 每个随机任务生成后验证不变量。
5. 给玩家真实选项；不要在题目文本或语音中提前说出答案。
6. 完成一关后明确进入下一关，最后一关才进入整轮结算。

对教育游戏，随机题必须先由确定性规则生成，再由 seed 提供可复现性。不要让大模型进入儿童实时判题路径。

## 第五步：加入声音、动画和儿童反馈

按照“状态提交 → 视觉变化 → 音效 → 语音 → 解锁下一步”的顺序组织反馈。

- 点击数字时读出数字或数量；
- 进入题目后延迟约 0.5 秒自动读题；
- 正确、错误、放置、掉落和完成使用不同音效；
- 语音使用可等待的队列，禁止后一段取消前一段；
- 语音播放期间锁定会造成重复提交的按钮；
- 音频不可用时立即解除锁定，不能卡死流程；
- 减少失败惩罚，使用“再数一次”等可执行提示。

动画只能表现已经提交的状态变化。动画中断不能导致数学状态或游戏状态丢失。

## 第六步：在真实浏览器中试玩

用户指定 Chrome 时使用本地 Chrome，并遵守对应浏览器 Skill。至少走一遍完整玩家路径，不只检查首页或完成页。

对每次截图反馈：

1. 先指出截图对应的具体游戏状态。
2. 判断问题是布局、状态选择器、缓存、数据还是交互时序。
3. 检查同一组件在开始、进行、错误、正确、完成和移动端状态。
4. 修改后复现用户截图中的同一状态再比较。
5. 最后保留可交付的浏览器页面。

Service Worker 或静态缓存存在时，每次前端资源更新都要同步更新缓存版本，避免“代码已改但用户看不到”。

## 第七步：验证并交付

按风险运行语法检查、领域测试、集成测试、浏览器流程和视觉检查。修复测试本身的问题时，不要削弱真实约束。

交付前确认：

- 游戏可从头到尾完成；
- 随机题多次重开会变化且合法；
- 错误选择不会修改真实状态；
- 所有固定数字、关卡名称和语音都已数据化；
- 工作树只包含本次修改；
- 服务状态符合用户要求；
- 只有在用户已授权或既定工作流要求时才提交和推送。

最终回复先说明完成结果，再给出验证证据、提交信息和仍在运行的服务。不要让用户依赖已折叠的中间更新。

## 每一步的沟通格式

保持更新简短，并包括：

```text
当前结论：这一阶段得到什么
正在处理：下一项具体工作
验证标准：用户如何判断完成
```

遇到截图或试玩反馈时，先承认可验证事实，再解释根因并修复。避免只说“已调整”；要说明影响的是哪个游戏状态以及如何复现。
