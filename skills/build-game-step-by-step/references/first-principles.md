# 游戏开发第一性原理

## 目录

1. 最小价值
2. 状态不变量
3. 交互与反馈
4. 随机内容
5. 音频与动画
6. 儿童与教育游戏

## 1. 最小价值

一个游戏首先必须回答：

- 玩家重复做什么？
- 为什么愿意再做一次？
- 操作后什么状态发生了可见变化？
- 玩家如何知道自己做对、做错或完成？

功能列表不能替代核心循环。先让一个循环可玩，再扩场景、关卡和奖励。

## 2. 状态不变量

为每个游戏写出不可破坏的等式或状态关系。例如数量游戏：

```text
当前数量
= 已放置单位积木
= 屏幕数字
= 合法槽位中的实体
= 语音读出的数量
= 保存和学习记录中的数量
```

通用规则：

- 领域状态是唯一事实源。
- UI、动画、音效和存储只读取领域状态。
- 一次玩家动作最多提交一次状态变化。
- 动画开始前先提交状态；动画失败不能回滚有效操作。
- 拖动取消、误触和设备卡顿不是游戏失败。

审查代码时搜索硬编码数字、重复状态字段和由 DOM 反推业务状态的逻辑。

## 3. 交互与反馈

每个操作都应形成：

```text
意图 → 校验 → 状态提交 → 反馈 → 下一可用动作
```

错误选择不得静默无响应。它应：

1. 不修改真实状态；
2. 播放温和反馈；
3. 告诉玩家下一步做什么；
4. 在反馈完成后重新开放操作。

用户报告“按钮没反应”时，依次检查：

- DOM 属性是否被当成布尔值错误判断；
- 按钮是否仍处于锁定状态；
- 语音 Promise 是否永远不结束；
- 点击和拖动是否走了不同逻辑；
- Service Worker 是否仍提供旧资源。

## 4. 随机内容

随机不是“每个字段独立 Math.random”。先定义合法候选，再随机选择。

建议结构：

```text
约束 → 枚举/生成候选 → 排除近期指纹 → seed 选择
→ 派生答案与选项 → 验证不变量 → 冻结任务
```

随机任务至少保证：

- 答案由题目状态派生；
- 不产生负数、越界或无法完成的任务；
- 正确选项一定存在且唯一；
- 干扰项不重复；
- 同一个 seed 可复现；
- 连续任务和重开后的最近任务不会完全重复；
- 画面能容纳生成的最大数量。

教育游戏中，题目生成与判定必须由确定性代码完成。

## 5. 音频与动画

音频状态机必须处理：

- 用户手势前浏览器禁止播放；
- 上一段语音被替换；
- 语音成功结束；
- 语音失败；
- 用户关闭语音；
- 页面隐藏或重开。

可等待语音必须在所有路径 resolve，不能让按钮永久锁定。

推荐时序：

```text
状态变化 → 短音效 → 必要动画 → 一段完整语音 → 解锁
```

不要用多段会相互取消的语音拼一句话。掉落多个实体时，每个实体播放一次短促、留有音量余量的音效。

## 6. 儿童与教育游戏

- 一次只突出一个主要动作。
- 触控目标至少约 56×56 CSS px。
- 文字短、语音清楚、无需计时催促。
- 数字必须与实际实体一一对应。
- “2 块”必须显示两个独立实体，不能显示一块写着 2 的实体，除非明确教学“数字积木代表数量”。
- 题目必须提供可选择内容，但不能提前读出正确答案。
- 答错不扣除已建内容，不用羞辱性声音。
- 第三层提示可共同完成，但仍让儿童执行最后一步。
