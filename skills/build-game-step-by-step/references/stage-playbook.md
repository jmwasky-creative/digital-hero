## 1. 阶段与出口条件

| 阶段 | 核心产物 | 出口条件 |
|---|---|---|
| 需求归一化 | 约束、用户、核心循环、首版范围 | 没有互相矛盾的核心规则 |
| 设计说明 | 状态、流程、交互、内容、音频、验收 | 开发者能据此实现同一游戏 |
| 实施计划 | 任务、依赖、接口、风险、测试 | 每项都有明确文件或交付物 |
| 技术切片 | 一条完整可玩路径 | 能从开始玩到完成并重玩 |
| 内容扩展 | 关卡数据与随机规则 | 多次运行合法且不连续重复 |
| 体验增强 | 音频、动画、响应式、无障碍 | 反馈不重叠、触控可用 |
| 浏览器验收 | 真实操作记录与截图 | 正确、错误和完成流程通过 |
| 交付 | 测试、提交、推送、运行状态 | 工作树和服务状态明确 |

## 2. 文件与模块边界

推荐把易变表现与稳定规则分离：

```text
game/
  domain/       数量、碰撞、得分、任务约束
  content/      关卡、题库、随机 seed、文本键
  presentation/ 场景、动画、声音映射
  storage/      快照、事件、同步
  ui/           页面、Canvas、输入适配
tests/
  domain/
  integration/
  browser/
```

小项目可以减少目录，但不能让 UI 同时承担出题、判题和状态保存。

先定义共享接口：

- `GameState`：唯一事实源；
- `TaskSpec`：输入、合法操作、答案和 seed；
- `GameEvent`：玩家意图与状态变化；
- `FeedbackPlan`：音效、语音和动画；
- `Snapshot`：可恢复状态。

## 3. 多 Agent 协作

只在用户明确要求或环境允许时使用。推荐边界：

- 领域 Agent：状态模型、随机生成器、领域测试；
- 前端 Agent：渲染、交互、响应式；
- 平台 Agent：音频、存储、服务、集成测试；
- 主 Agent：读需求、定义接口、解决冲突、浏览器验收、提交。

不要让多个 Agent 同时修改同一主文件。必须共享的接口先由主 Agent落盘，再并行。

## 4. 常见返工点

### 只改了一个状态

截图说“上移”，可能指进行中卡片，不是完成卡片。修改前确认截图中的阶段，并检查所有阶段选择器。

### 数字和实体不一致

任何“数量 N”都检查真实渲染实体是否有 N 个。数字牌是可选择的数量表示，单位积木是实际实体，两者不能混淆。

### 固定技术切片没有被数据化

扩关卡前搜索固定数字、关卡名、目标名和语音。把它们改为任务数据后再做随机生成。

### 随机题仍让人感觉重复

除 seed 外增加近期指纹窗口；跨重开保存最近指纹。测试不仅检查范围，还要检查可复现性、不变量和排重。

### 代码更新但浏览器没变化

检查 Service Worker、查询版本、浏览器缓存和正在运行的服务。前端资源变更后同步提升缓存版本。

### 语音被下一段打断

使用 `speakAndWait`；在成功、失败、取消、关闭和不支持路径都结束 Promise。反馈语句尽量一次完整朗读。

### 只有正确选项

题目必须提供多个合法显示的选项。干扰项不能改变状态；正确选项才触发状态提交。
